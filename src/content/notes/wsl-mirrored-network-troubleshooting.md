## TL;DR

本次 WSL 网络故障同时出现 IP 不通与 DNS 返回 fake-ip 的现象。排查时观察到 Meta 虚拟网卡；关闭安全软件的相关拦截后 IP 连通性恢复，关闭 Clash 的 TUN 后 DNS 返回结果恢复。日志不足以单独证明所有流量的具体拦截层。

修复方案：关闭 Clash TUN 模式，改用系统代理 + `autoProxy`，让 WSL 自动继承 Windows 代理设置。

## 现象

WSL2 Ubuntu 完全无法连接外网：

```bash
$ ping -c 3 8.8.8.8
# 100% packet loss, "Destination Host Unreachable" from 198.18.0.1

$ curl -I https://www.baidu.com
# 超时无响应

$ getent hosts baidu.com
198.18.0.51     baidu.com     # 假地址

$ getent hosts google.com
198.18.0.21     google.com    # 假地址
```

`198.18.0.0/15` 是 IANA 登记的 Benchmarking 特殊用途地址段；代理的 fake-ip 模式可能返回此类地址，不能仅凭这一结果判断网络是否故障。

## 环境

| 项目 | 配置 |
|------|------|
| OS | Windows 11 |
| WSL | WSL2, Ubuntu, networkingMode=Mirrored |
| 安全软件 | 火绒 |
| 代理软件 | Clash Verge (rev), 内核 verge-mihomo |
| `.wslconfig` | `dnsTunneling=true`, `firewall=true`, `autoProxy=false` |

## 排查过程

### 第一轮：怀疑火绒

逐项关闭火绒的网络防护功能：

| 操作 | IP 连通性 | DNS 解析 |
|------|-----------|----------|
| 初始状态 | ping 8.8.8.8 100% 丢包 | 劫持到 198.18.0.x |
| 关闭「对外 ARP 拦截」 | ping 通了，0% 丢包 | 仍然劫持 |
| 关闭「对外攻击拦截」 | 通 | 仍然劫持 |
| 关闭「恶意网址拦截」 | 通 | 仍然劫持 |
| 退出所有安全软件 | 通 | **仍然劫持** |

本次关闭火绒 ARP 拦截后 IP 层恢复，但 DNS 仍返回 fake-ip；仅凭这些观察不能排除所有其他因素。

关键测试 —— 指定外部 DNS 服务器查询：

```powershell
PS> nslookup baidu.com 8.8.8.8
Address:  198.18.0.51    # 即使走 Google DNS，返回的仍然是假地址

PS> nslookup baidu.com 1.1.1.1
Address:  198.18.0.51    # Cloudflare DNS 也一样
```

直接指定 8.8.8.8 / 1.1.1.1 做 DNS 查询，返回的仍然是假地址。这提示查询可能被本机网络或代理配置重定向，但不足以单独确定拦截层或排除其他原因。

### 第二轮：检查虚拟网卡

检查 Windows 网络适配器，发现一个可疑的虚拟网卡：

```powershell
PS> Get-NetAdapter -Name 'Meta' | Select-Object Name, InterfaceDescription, DriverFileName, DriverProvider, DriverVersionString, Status, LinkSpeed

Name   : Meta
InterfaceDescription : Meta Tunnel
DriverFileName       : wintun.sys
DriverProvider       : WireGuard LLC
DriverVersionString  : 0.14.0.0
Status               : Up
LinkSpeed            : 100 Gbps
```

**Meta Tunnel** —— 使用 `wintun.sys`（WireGuard LLC 的 TUN 驱动）创建的虚拟网卡。这是 Clash Verge 开启 TUN 模式时创建的适配器。

检查其 DNS 配置：

```powershell
PS> Get-DnsClientServerAddress -InterfaceAlias 'Meta'
InterfaceAlias  ServerAddresses
Meta            {198.18.0.2}
```

DNS 指向 `198.18.0.2`，正好在 `198.18.0.0/30` 子网内，和 WSL 里看到的 `eth1` 接口一致。

**本次判断**：虚拟网卡和 fake-ip 配置与现象有关；关闭 TUN 后 DNS 返回恢复。仅凭这些观察不能证明 `wintun.sys` 本身拦截所有流量，也不能推断退出界面后所有用户态程序均已停止。

### 第三轮：修复 DNS 劫持

在 Clash Verge 中关闭 TUN 模式后，DNS 立即恢复：

```bash
$ getent hosts baidu.com
111.63.65.103   baidu.com
111.63.65.247   baidu.com
110.242.74.102  baidu.com     # 真实 IP

$ curl -sI https://www.baidu.com | head -1
HTTP/1.1 200 OK

$ curl -sI https://github.com | head -1
HTTP/2 200
```

### 第四轮：让 WSL 走 Clash 代理

关掉 TUN 后 WSL 能直连外网了，但访问被墙的站点还需要走代理。

Clash Verge 的代理端口配置：

```yaml
mixed-port: 7897      # HTTP + SOCKS5 混合端口
socks-port: 7898
port: 7899
allow-lan: false       # 默认只监听 127.0.0.1
```

**本次观察**：当时尝试若干网关和主机地址访问代理端口未成功。微软文档说明 Mirrored 模式支持从 WSL 通过 `127.0.0.1` 访问 Windows 服务；以下结果是当时环境现象，不是该模式的通用限制：

```bash
$ curl http://10.122.0.1:7897      # 网关地址 → Connection refused
$ curl http://10.122.255.60:7897   # 共享 IP → Connection refused（连到了 WSL 自己）
$ curl http://198.18.0.2:7897      # Hyper-V 接口 → Connection timed out
```

在 Clash 中开启「允许局域网连接」后，Clash 监听 `0.0.0.0:7897`，但 WSL 仍然连不上。

**解决方案**：使用 WSL 的 `autoProxy` 功能。

编辑 Windows 用户目录下的 `%UserProfile%\.wslconfig`。以下是按当前文档整理的最小示例，原记录中的其他实验项不在此列：

```ini
[wsl2]
networkingMode=mirrored
dnsTunneling=true
firewall=true
autoProxy=true
```

重启 WSL：

```powershell
wsl --shutdown
```

重新进入 WSL，代理环境变量已自动注入：

```bash
$ echo $http_proxy
http://127.0.0.1:7897

$ echo $https_proxy
http://127.0.0.1:7897

$ curl -sI https://www.google.com | head -1
HTTP/1.1 200 Connection established

$ curl -sI https://www.youtube.com | head -1
HTTP/1.1 200 Connection established

$ curl -sI https://github.com | head -1
HTTP/1.1 200 Connection established
```

WSL 的 `autoProxy` 可使用 Windows 的 HTTP 代理信息，具体连通性仍需按本机配置验证。上述 `200 Connection established` 只说明代理 CONNECT 建立，不能单独证明目标网站已成功响应。

## 关键排查技巧

```bash
# 1. 测试 IP 层连通性（排除 DNS 问题）
ping -c 3 8.8.8.8

# 2. 指定外部 DNS 查询，结合代理与网络配置继续排查
nslookup baidu.com 8.8.8.8
# 返回 fake-ip 时，应继续检查配置；该结果不能单独定位拦截层

# 3. Windows 端检查可疑虚拟网卡
Get-NetAdapter -IncludeHidden | Where-Object { $_.Virtual -eq $true -and $_.Status -eq 'Up' }

# 4. 查看虚拟网卡详情（驱动、提供商）
Get-NetAdapter -Name 'Meta' | Select-Object Name, InterfaceDescription, DriverFileName, DriverProvider

# 5. 检查各网卡的 DNS 配置
Get-DnsClientServerAddress -AddressFamily IPv4

# 6. 查看端口监听状态
netstat -ano | findstr LISTENING | findstr "7897 7890"

# 7. WSL 内检查代理变量是否生效
echo $http_proxy && echo $https_proxy
```

## 总结

| 问题 | 原因 | 解决 |
|------|------|------|
| ping 不通 | 火绒 ARP 拦截 | 关闭「对外 ARP 拦截」 |
| DNS 返回 198.18.0.x | 当时的 TUN 与 fake-ip 配置相关 | 关闭 TUN 后观察到恢复 |
| WSL 无法走代理 | 本次代理信息未按需要配置 | `.wslconfig` 设置 `autoProxy=true` + 重启 WSL |

核心教训：遇到 `198.18.0.x` 段的 DNS 解析结果，第一时间检查是否有 TUN/VPN 虚拟网卡在运行。用 `nslookup domain 8.8.8.8` 指定外部 DNS 查询可提供额外线索，但不足以单独定位拦截层。
